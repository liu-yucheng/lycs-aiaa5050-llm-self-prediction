Design of the experiment

The research question, the two hypotheses, the four conditions, and the rules that keep the comparison honest.

The hypotheses

The null hypothesis. The self report agrees with the served table. The divergence is near zero, and self-prediction is an emergent property of next-token training.

The alternative hypothesis. The divergence is significantly larger than zero. The model predicts text well and its own table badly.

A verdict never proves either hypothesis. It states whether the observed sample supports a difference that is larger than the tolerance.

The four conditions

ConditionContextTable origin
plain_actualThe task prompt.The provider logprobs of one served token.
plain_selfThe task prompt.The JSON table in the reply body.
injected_selfThe task prompt, then one assistant message with a served table.The JSON table in the second reply body.
injected_actualThe task prompt, then one assistant message with a self report.The provider logprobs of the following served token.

The repetitions

Each condition runs three times for each task. The temperature is zero, so the served table of one model changes little across repetitions, while a self report can change a lot. Both kinds of repetition appear in the comparison.

One comparison pairs each actual repetition with each predicted repetition. Three repetitions give nine pairs for each task and each comparison.

The dataset

The dataset holds two files in inputs/testing-dataset/. One file holds 32 Simplified Chinese tasks. The other file holds 32 US English tasks. Each file spreads its tasks over eight categories: poetry, idiom, daily, food, weather, technology, news, and story.

A task holds an identifier, a category, a language, a sentence prefix, and a reference token. The reference token is the token that a human writer would choose next. The plugin validates the dataset and rejects a prefix that already ends with its reference token. No metric reads the reference token, so a wrong completion cannot flatter or spoil a divergence.

The run flow

  • Read the workspace, the dataset, the environment file, and the provider catalog.
  • Expand each provider that lists several models into one client for each model.
  • Resolve the API key of each client and stop with a prompt when a key is absent.
  • Probe each client with one served table and leave out a model that reports no table.
  • Create the run directory and write run.json and tasks.json.
  • Run one job for each task and client pair, with a bounded worker pool.
  • Write the raw exchange of each call before the plugin parses the reply.
  • Compute the three comparisons, the summaries, and the bootstrap intervals.
  • Write the metrics, the records, the report, the tables, and the demonstration website.

The integrity rules

  • The plugin never edits a raw reply. The parse result lives in a separate file.
  • The plugin never changes a prompt or a dataset task to make a metric pass.
  • The plugin records the plugin version, the Node.js version, the platform, and the seed.
  • A failed call becomes one failure line in the task record, and the run continues.
